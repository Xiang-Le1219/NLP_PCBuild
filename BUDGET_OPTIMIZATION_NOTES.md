# Budget optimisation update

## What changed

The prior engine selected the CPU/GPU combination primarily by workload-performance score, with only a mild penalty for spending. It also disabled discrete GPUs for office/general/programming profiles unless the user explicitly requested a GPU. As a result, those light-use profiles could leave a large unused balance even with a high budget.

The updated engine and Streamlit interface now provide two explicit strategies:

1. `closest_to_budget` (default): select the highest compatible catalogue total below the available budget. The budget is the primary ranking objective; workload performance is a tie-breaker. It may include an optional discrete GPU for office/general/programming requests to use more of the budget. The app displays a warning because this may be unnecessary for those workloads.
2. `best_value`: retain the previous workload-oriented selection. For light workloads it may intentionally spend less because an expensive discrete GPU is not necessary.

A MYR 0.01 display buffer is left below the budget so rounding to two decimals does not show a total equal to the budget. All generated totals are checked to remain strictly below the budget.

## Tested examples

All amounts below are from the supplied catalogue and fixed USD-to-MYR assumption (4.30), not live retail prices.

| Use case | Strategy | Budget | Generated total | Remaining |
|---|---|---:|---:|---:|
| Gaming | Closest under budget | RM5,000 | RM4,999.65 | RM0.35 |
| Gaming | Closest under budget | RM10,000 | RM9,996.17 | RM3.83 |
| Office | Closest under budget | RM10,000 | RM9,997.16 | RM2.84 |
| Office | Best value | RM10,000 | RM2,003.76 | RM7,996.24 |

The office closest-to-budget build includes a discrete GPU; this is an optional performance upgrade and may be excessive for basic office work. Users should select Best value when power efficiency and suitability matter more than using the entire budget.

## Regression tests

- `python test_budget_strategy.py`: 28 scenarios across seven use cases, two budgets and both strategies.
- `python smoke_test.py`: natural-language baseline and build validation scenarios.
- `python -m py_compile app.py advisor.py pc_engine.py nlu_data.py opt_nlu.py`: syntax check.

These tests exercise the local recommendation engine. They do not verify live retail pricing, all physical hardware clearances, OPT model download/training, or Streamlit Cloud resource limits.

## What the three NLP modes mean

- **Rule-based baseline:** keyword and regular-expression extraction; no Transformer inference.
- **Pretrained OPT-125M (few-shot):** unmodified OPT-125M with example prompts at inference time.
- **Fine-tuned OPT-125M (LoRA):** OPT-125M plus the supplied `adapters/extract_125m` adapter for structured PC requirement extraction.

The NLP mode selector affects requirement extraction only. Product selection and the budget strategy are handled by `pc_engine.py`. The displayed build explanation is a deterministic template, not generated by OPT.


## Additional requirement-extraction safeguard

OPT is no longer trusted to invent a budget when the user did not state one. Both the deployment adapter path (`advisor.py`) and notebook NLU wrapper (`opt_nlu.py`) now overwrite an OPT-extracted budget with the value found by deterministic parsing; if no explicit amount appears, the budget remains unset and the user must enter it in the review form. This prevents a guessed default such as RM5,100 from silently controlling the recommendation.
